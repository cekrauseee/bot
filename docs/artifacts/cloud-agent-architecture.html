Cloud agent architecture

A durable agent loop with a shared user filesystem, run-scoped browsers, and a task interface. This map separates implemented capabilities from the pieces still needed for a complete cloud workspace.

Task = conversation Run = one execution within a task Workspace = shared files for one user

One execution path, separate responsibilities

What the agent can do

Implemented in code. Expand a capability for its tools and limits.

Work with shared files and processesDiscover files, read text, write files, and execute commands.
  • filesystem_list, filesystem_read, and filesystem_write operate on UTF-8 files under /workspace.
  • shell_exec runs an executable with explicit argv and cwd. Bash is possible as an executable; shell syntax is not implicitly interpolated.
  • Tasks belonging to one user share files. The local runtime queues workspace operations; there is no automatic Git or file-conflict workflow.
  • The agent shell runs as unprivileged mybot-agent. The root-only operation journal lives outside the workspace.
Operate a browserNavigate, inspect, click, type, and show what changed.
  • browser_open, browser_snapshot, browser_click, browser_type, and browser_close use agent-browser inside the sandbox.
  • Each run has a distinct browser session. A recreated runtime controller can reattach to that session.
  • Actions may emit a bounded PNG frame. The UI shows it in a run-scoped picture-in-picture preview while the browser is active.
  • Frames are action-driven, not continuous video. They are removed from model tool results and are not saved in PostgreSQL or the journal.
Maintain one macro task planA persistent badge above the composer, not a message block.
  • update_plan replaces the task's current list of pending, in-progress, and completed steps.
  • The latest nonempty run snapshot supplies the single task plan. New runs inherit it and receive it as root-agent context.
  • The badge expands into a step popover. It survives completion, navigation, reloads, and later turns.
Ask blocking questionsNormal conversation text with no special protocol.
  • The root agent asks only when missing information materially affects the result or risk, using normal prose or bullets as needed.
  • The question is a normal assistant message and completes the current turn.
  • The user's answer starts a normal subsequent turn with the conversation transcript as context.
Delegate to child agentsBounded task context with model-level controls.
  • delegate_to_child_agent accepts a task plus optional model, reasoning effort, and speed.
  • Children receive their bounded task, runtime tools, and recursive delegation. They do not receive the root's plan tool.
  • Stable checkpoint namespaces support recovery without replaying a completed child task. The current depth limit is four child levels.
  • Child start/completion activity is visible. A graph editor and richer context/permission policies are not implemented.
Continue beyond the current viewBackground execution, reconnect, and normalized output.
  • Leaving a task detaches the view without cancelling its run. Returning hydrates the active run and plan.
  • The interface subscribes to the selected run and reconnects using a durable decimal event cursor.
  • Text, safe reasoning summaries, searches, runtime tools, and child activity have normalized events. OpenAI also has built-in web search.
  • Model selection adapts reasoning and Fast controls for the supported GPT models.

Shared files do not mean shared browser state

One user → one global workspace

  • Task A and Task B can use the same /workspace files.
  • Each task has its own messages and one macro plan.
  • Projects link conversations to stable folders under /workspace/projects/, prepared on first file or shell use. Each run keeps its initial directory after a conversation moves; other workspace files remain accessible.

Each execution → its own run state

  • Run A → checkpoint, event cursor, browser session A.
  • Run B → checkpoint, event cursor, browser session B.
  • Only one active run per conversation; different conversations can remain active in the background.

How a run stays durable

Queued→ Running→ Completed / Failed / Cancelled

Checkpoint decides execution

No checkpoint: submit the transcript. Runnable checkpoint: continue existing state. Completed checkpoint: project the result without calling the model again.

Lease protects persistence

The API renews an execution lease. An expired lease can be reclaimed; an old executor cannot write with a stale token. Checkpoint reconciliation replaces stale partial text before new deltas.

Journal protects effects

Deterministic operation IDs replay completed results. An ambiguous shell/browser effect requires manual recovery. Cancelled queued work is checked again before dispatch; already-started effects follow provider semantics.

Iteration map: what is not finished yet

Future runtimesNo desktop filesystem adapter, dedicated user VM provisioning, Git integration, or full desktop streaming.Keep these behind the existing runtime boundary rather than changing the agent loop.

One current stack: LangChain/LangGraph for orchestration; Node/Elysia for the product API; Node + Vercel Sandbox for tools; PostgreSQL for durable state; Redis for fanout; React with shadcn/Base UI for the interface.

Just Bash, a separate app-level Playwright integration, per-user Docker provisioning, and a custom behavior harness were not added. Turbo owns JavaScript tasks; uv owns Python dependencies. Local Docker Compose runs PostgreSQL and Redis.

Scope: the cloud-agent foundation and shared project-folder integration. This is an implementation map, not a claim that every provider is configured or every future capability is available.
